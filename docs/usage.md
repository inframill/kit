# Using Kit

## Inframill CLI

`inframill server start` starts the daemon; `inframill server version` queries its
version. Resource commands are top-level: `inframill namespace`, `instance`,
`blueprint`, `secret`, `registry`, `execution` and `provider`. They send requests
to the daemon. Shell completion uses `inframill completion`; `inframill debug provider`
runs the offline debug provider protocol. Kit's providers share `kit-exec`, selected
by an exact `NAME-VERSION` prefix argument.

Only server startup accepts `--config` (default `.inframill.yaml`). Relative data, local blueprint search
and provider paths resolve beside that file. The `connect-engine` handler accepts
an optional `rootToken`; its route is fixed. Resource requests and `server version` accept `--endpoint` and `--timeout`,
falling back to `INFRAMILL_ENDPOINT` and `INFRAMILL_TIMEOUT`, then
`http://127.0.0.1:8080` and `2m`. Requests reject `--config` and never load YAML.
Request flags belong to resource groups and `server version`, not the root,
`server start`, `completion` or `debug` groups. Generate shell completion with
`inframill completion zsh` and load the output through your shell's completion
configuration. Regenerate completions after upgrading Inframill.

`inframill provider list` reports the daemon's cached startup availability.
Restart the daemon after changing its provider configuration.
`inframill server version` reports the selected daemon's build version;
`inframill --version` reports the local CLI version.

## Daemon authentication

The image and generated native configurations serve unauthenticated HTTP by
default. To require a root token, configure the handler:

```yaml
handlers:
  - type: connect-engine
    settings:
      rootToken: ${ROOT_TOKEN}
```

Supply `ROOT_TOKEN` in the server environment and in the CLI environment. Other
clients send the same value in `X-Root-Token`. The token grants full engine access;
missing or incorrect tokens return HTTP 401. An empty configured token or a
missing environment reference fails startup. Restart the daemon to rotate it.
Keep the token out of command arguments and checked-in files. For remote access,
use TLS through `main.tls.certFile` and `main.tls.keyFile`, or an authenticated
gateway or private tunnel. The pv-cloud worker payload configures native TLS
and root-token authentication.

## Namespace events

Read a page of resource changes or watch new changes as JSON Lines:

```sh
bin/inframill namespace events read --namespace production --after-sequence 0 --limit 100
bin/inframill namespace events watch --namespace production --timeout 24h
bin/inframill namespace events watch --namespace production --after-sequence 42 --timeout 24h
```

Watch without a position starts at the current tail; explicit zero replays retained
history. Read pages expose `nextSequence` for pagination. Sequences and execution
revisions are decimal strings; retain their full integer precision. On
`resyncRequired` or `stream.reset`, refresh current resource queries. Events include
credential identifiers but omit credential values, command arguments/results and
log output. Positions belong to one namespace lifetime and must be discarded after its deletion.

Each namespace persists its feed in `data.sqlite`. History is unlimited by default.
To enable retention, add `eventJournalMaxBytes: 67108864` under `engine` in your
daemon configuration, then restart. Zero disables retention; nonzero limits must
be at least 131072 bytes. The limit measures encoded event bytes, not physical
SQLite file size. Enabling or lowering the limit can prune existing history.
Expired positions explicitly request a refresh. The normal total CLI timeout
applies to watches; reconnect explicitly after the last event you processed.

## Running a deployment

Run these commands from the repository root. `blueprints/examples/pv-cloud.json`
contains plain Values JSON for `data-1`, `worker-1`, and `web-1`. Their roles select
the PostgreSQL, Inframill and Millway Dispatch payloads, respectively.
Replace the example's `tls.certificate` placeholder with your public certificate
chain and store its private key and root token as the namespace secrets
`pv-cloud-tls-private-key` and `inframill-root-token`.
Set `cloudflare.zone_name` to match its zone ID, configure the Millway image and
Google client IDs, and store Millway's separate API token as `millway-root-token`.
Store the required application passwords as `app1-password` and `app2-password`;
they are injected during the PostgreSQL push and are never generated by start.
The same Blueprint
supports either architecture or a mix, selected per node. Prepare the native
binaries and local tools, generate configuration, then start the daemon:

```sh
toolai go build --native --output bin/kit-exec
task build:engine
task setup
task --silent config > /tmp/kit-config.json
bin/inframill server start --config /tmp/kit-config.json
```

In another terminal, create a namespace, fetch a local blueprint and initialize an Instance.
Initialization validates Values, checks required namespace secret names and renders
files without executing a provider:

```sh
bin/inframill namespace create production
bin/inframill blueprint fetch built.in/pv-cloud:0.10.0 \
  --namespace production
bin/inframill secret upsert --namespace production --file /private/path/app1-password.json
bin/inframill secret upsert --namespace production --file /private/path/app2-password.json
bin/inframill secret upsert --namespace production --file /private/path/hetzner.json
bin/inframill secret upsert --namespace production --file /private/path/cloudflare.json
bin/inframill secret upsert --namespace production --file /private/path/pv-cloud-tls-private-key.json
bin/inframill secret upsert --namespace production --file /private/path/inframill-root-token.json
bin/inframill secret upsert --namespace production --file /private/path/millway-root-token.json
bin/inframill secret upsert --namespace production --file /private/path/pv-cloud-registry-token.json
bin/inframill instance init example --namespace production \
  --blueprint built.in/pv-cloud:0.10.0 \
  --values-file blueprints/examples/pv-cloud.json
bin/inframill instance exec example --namespace production opentofu.init --wait
```

The generated configuration uses the pinned local tools by default;
`OPENTOFU_PATH` and `ANSIBLE_PATH` can override their absolute paths.
It allows the local `blueprints/` directory.
`built.in/pv-cloud:0.10.0` selects the current blueprint release.
`built.in/pv-cloud` selects `blueprints/pv-cloud/latest/`; append `:TAG` to use
`blueprints/pv-cloud/TAG/`. These references require no registry. Re-fetch after
editing source files and initialize a new Instance to use the new snapshot. Commands such as init/plan/apply contact
real services and require your chosen credentials and infrastructure inputs.
Use `--arguments '{"playbook":"site"}'` for inline execution arguments or
`--arguments-file` for a file (the two flags are mutually exclusive), `--wait` to wait for an outcome and
`-o json` for structured output. A failed command has a failed outcome; cancelling
or timing out a client wait does not cancel admitted work or roll back tool effects.
Creation inputs are immutable; use a new Instance name to change them.

To follow live stdout and stderr until completion, use `--stream`:

```sh
bin/inframill instance exec example --namespace production opentofu.init --stream
```

`--stream` implies waiting and keeps stdout raw; status notices accompany stderr.
It rejects JSON output and `builtin.cancel`/`builtin.delete`. Stopping the CLI leaves admitted work
running and prints continuation commands with independent log offsets.

To check local sources, run
`BLUEPRINT=pv-cloud python3 tests/check.py blueprint:check`: it starts a disposable
daemon, fetches the source directory, renders examples, checks Ansible syntax and
runs OpenTofu provider mocks. The installed local tools are required; no blueprint
registry is involved. For Docker development, `task docker:up` mounts `blueprints/`
at the configured `/opt/inframill/blueprints` path. See [local blueprints](../blueprints/README.md).

Inspect providers, Instances and command history with:

```sh
bin/inframill server version
bin/inframill provider list
bin/inframill instance list --namespace production
bin/inframill provider commands
bin/inframill provider commands opentofu.plan
bin/inframill instance commands example --namespace production
bin/inframill instance commands example opentofu.plan --namespace production
bin/inframill execution list --instance example --namespace production --all -o json
bin/inframill execution get EXECUTION_ULID --instance example --namespace production
bin/inframill execution wait EXECUTION_ULID --instance example --namespace production
bin/inframill execution logs EXECUTION_ULID --instance example --namespace production --follow
```

Instance inspection (`instance get`) and execution accept a local name or canonical uppercase ULID.
Both require `--namespace`, including ID-based operations.
Execution history uses `--instance`. `provider commands` lists cached commands
across all available providers, without running tools or checking secrets.
`provider commands NAME` shows one command's description and access mode.
`instance commands INSTANCE [NAME] --namespace ID` includes the supported commands
and their Blueprint-owned argument schemas, plus engine-owned built-ins. Global
Provider discovery has no Instance scope and does not guarantee applicability to
an Instance. Use `instance delete` to delete an Instance.
Logs default to raw stdout; add `--stream stderr` for stderr. JSON log output is a
single snapshot and cannot use `--follow`. Paginated Instance and execution lists
support `--all`, with `--limit` controlling page size under one total timeout.
If a wait times out, use the printed ULID-based reconnect command to resume waiting;
the admitted execution continues on the daemon.

## Namespaces

Namespaces must exist before initializing Instances, managing blueprints or
setting credentials. Create each namespace once with `namespace create ID`;
`namespace list` includes empty namespaces and persists across restarts.
Every namespace-owned operation requires `--namespace`, including lists and
Instance/execution ID lookups. Instance names are local to that namespace;
qualified `namespace/name` selectors and namespace defaults are unsupported.

```sh
bin/inframill namespace list
bin/inframill namespace get production
bin/inframill instance list --namespace production
bin/inframill blueprint list --namespace production
bin/inframill secret list --namespace production
bin/inframill registry list --namespace production
```

Scoped output omits namespace identifiers. Credential lists expose names or hosts
and creation timestamps, never values. Namespace create/get/delete take a positional
namespace ID; namespace administration, server version and provider discovery reject
`--namespace`.
Queries read the daemon's local inventory and do not fetch remote resources.

Namespace IDs accept `[a-zA-Z0-9-]+` and preserve case. IDs beginning with a hyphen
use `namespace create -- -Team-` and `--namespace=-Team-` in scoped CLI commands.
Instance names and Provider/command identifiers use the same character grammar;
instance and execution IDs remain ULIDs. Blueprint inputs have separate schema rules.
Namespace RPC create/get/delete bodies and metadata use `id`, for example
`{"id":"production"}`. Stored namespace records also
use `id`; old `name` records reject without migration. Preserve old data and use a
fresh data directory or volume when upgrading.

Each namespace owns `<dataDir>/<namespace>/namespace.json`, `data.sqlite`, `blueprints/` and
`instances/<InstanceID>/`. Fetch a blueprint separately into every namespace that
uses it; catalogues and cached content are isolated.

Existing namespaces initialize in the background after daemon startup. Use
`namespace get ID` to inspect `loading`, `ready` or `failed` status and results for
Events, Secrets, Registries, Blueprints and Instances. Scoped operations require
`ready`; namespace creation initializes synchronously. Instance history recovers
during namespace initialization, and Instance responses include execution counts.

`namespace delete ID` marks the namespace deleted and waits for admitted work to
drain and resources to close. New work rejects with a deleted-namespace error and
normal namespace/scoped reads return not found. All stored files remain; there is
no cleanup worker or undelete API.
The namespace ID stays reserved and cannot be recreated.

Instances report `ready`, `running` or `failed`, with creation/update timestamps.
`instance cancel INSTANCE --namespace ID` kills running commands and cancels queued
commands, recording `cancelled` with a reason and cancellation timestamp while
retaining the Instance and history. Uncancelled signal death records
`interrupted/process_signalled`; restart recovery records `interrupted/daemon_restarted`.
`instance delete` also hides the Instance from normal reads immediately and retains its files. Both return after
process termination and saved outcomes; `--wait` is redundant and `--stream` rejects.
Deleted Instance names can be reused with a new ULID. Neither operation destroys
external infrastructure; run the appropriate provider destroy commands first.

`instance rerender INSTANCE --namespace ID --values-file FILE --wait` replaces all
Values and regenerates the workspace from the saved Blueprint. It preserves
identity, source, artifacts and history, but removes Provider-created workspace
files. Local OpenTofu state lives in artifacts and survives rerender. Run
`opentofu.init` after rerender to reinitialize the backend and provider plugins.
For existing Instances whose state is still in the workspace, run `opentofu.init`
with the updated provider before rerender to migrate it into artifacts.

Prior namespace and command storage formats reject without modification or
migration. Preserve old data and use a fresh data directory for this release.

## Namespace registry credentials

Every blueprint fetch requires `--namespace`. Local Kit blueprints do not need
registry credentials. For other private OCI blueprints, supply registry credentials
to an existing namespace before fetching:

```sh
bin/inframill registry upsert --namespace production --file /private/path/registry.json
bin/inframill registry list --namespace production
bin/inframill blueprint fetch ghcr.io/example/blueprints/custom:1.0.0 \
  --namespace production
```

The credential file contains one complete registry entry, for example:

```json
{"host":"ghcr.io","username":"example-user","password":"synthetic-token"}
```

Credentials persist unencrypted in namespace `data.sqlite`, including across restart
and namespace deletion. `registry delete ghcr.io --namespace production` deletes one
entry. An unmatched host uses anonymous access. The daemon does not load Docker login credentials, and
registry credentials remain separate from provider secrets. Blueprint cache
entries belong to the selected namespace. Fetch errors include structured
diagnostics for authentication, access, missing references and network failures.

## Namespace secrets

Each secret file contains one entry: `{"name":"hetzner","value":"synthetic-token"}`.
The pv-cloud example uses `hetzner` for its cloud API token and `cloudflare` for
its Cloudflare API token. Store the latter with a separate secret entry such as
`{"name":"cloudflare","value":"synthetic-cloudflare-token"}`. Values set
`cloudflare.zone_id`; each node gets a DNS-only A record
named `<node>-<lowercase-instance-id>.<zone>` pointing to its public IPv4. The token
needs permission to edit DNS records and read the selected zone. pv-cloud `0.10.0`
and `latest` also require `app1-password`, `app2-password`,
`pv-cloud-tls-private-key`, `inframill-root-token`, `millway-root-token`, and
`pv-cloud-registry-token`. All eight names are declared in the Blueprint's
`required_secrets`; provider settings refer to those namespace names.
Values contain no credential values. PostgreSQL database entries can select a
password secret by name with `password_secret`. Initialization requires
their presence in the selected namespace, even without worker nodes or registry
login settings, and reports
all missing names with `MISSING_SECRET`. Add the missing entries and retry with
the same Instance name. Presence does not validate credential contents.
Inframill supplies a namespace snapshot only to provider Execute; Kit does not
read `INFRAMILL_SECRET_*` or arbitrary inherited tool credential variables. Required
credentials must be nonempty and are checked before effects. Only selected values
reach the tool environment. Known injected values are filtered from tool diagnostics;
Kit results and shared artifacts contain only verified projections. Arbitrary
provider/playbook output must not intentionally emit transformed secrets.

Manage entries with `secret upsert`, `secret list` and `secret delete NAME`, using
`--namespace production`. Secrets persist unencrypted in namespace `data.sqlite`
and its sidecars across restart and namespace deletion. Upsert preserves creation
time; lists return oldest entries first. Running commands retain their snapshot;
queued commands obtain current secrets when they start.

The `InitInstance` RPC requires the HTTP header `X-Namespace-ID: production`
and accepts these top-level fields:

```json
{"name":"example","blueprint_reference":"built.in/pv-cloud","values":{"json":"{}"}}
```

Set `values.json` to the serialized Values JSON. The CLI still accepts plain Values files. Fetch the blueprint before
initializing the Instance in the same existing namespace. Blueprint list/get reports ready and failed catalogue
entries; resolve requires a usable revision. Deleting a cached revision by its digest pin
preserves existing Instances and their source snapshots.
With `-o json`, `blueprint get`, `provider get` and `provider commands NAME` return the selected
resource directly; `blueprint resolve` returns `blueprint` metadata and the raw
Values schema as an ordinary `valuesSchema` object. Blueprint metadata also
publishes `commands`, each with a name and argument schema. RPC wraps schemas in
`JsonDocument` envelopes; CLI JSON unwraps them. Human Blueprint details show a
Command arguments section, and `blueprint resolve` also shows the Values schema.
Blueprint metadata also exposes declared `features` as sorted identifiers; an empty
list may be omitted in JSON. Human details and list output display these capabilities.

## Providers

A blueprint has a static `blueprint.yaml` containing `api_version`, `description`,
an inline `values_schema`, `command_arguments`, and `provider_settings`, alongside `templates/`.
Each entry has a required major.minor version and nested provider settings:

```yaml
command_arguments:
  opentofu.init:
    type: object
    additionalProperties: false
provider_settings:
  opentofu:
    version: "0.4"
    settings:
      id: opentofu
      settings_file: kit-provider.json
      backend: local
      node_output: inframill_nodes
      artifact: opentofu-nodes-v1.json
```

Inframill checks the connected provider's major/minor before accepting the Blueprint.
The compiled catalog selects exact provider releases; the Blueprint binding declares the
compatible major/minor line.
Templates render nonsecret settings into `kit-provider.json` within
`workspace/opentofu/` and `workspace/ansible/`. Sources live in matching
`templates/opentofu/` and `templates/ansible/` directories. The engine supplies
each provider's directory directly; providers do not append another directory.
Secret references are names in settings files, never credentials.
Settings validation uses no files. Blueprints explicitly select supported commands
and own their argument schemas through `command_arguments`. Inframill validates
arguments before admission using the Instance's retained revision, without provider
subprocesses or secret access. Execute receives arguments and the namespace secret
snapshot directly, checks rendered inputs and prerequisites before effects, then
performs and verifies the operation.

OpenTofu supplies init, validate, plan, apply and destroy. Plan returns a
`plan_id`; apply/destroy accept it optionally. With an ID, Kit validates and consumes
that exact saved plan. Plans bind the shared artifact directory,
provider/tool/configuration and source bytes. Kit retires a saved plan before apply
effects, so failures and partial effects require a fresh plan.

Without `plan_id`, apply/destroy plan and execute the current configuration in one
noninteractive operation using OpenTofu's `-auto-approve`. They do not select a
previously saved plan. An explicitly supplied ID must be valid and available;
invalid, stale or missing saved plans fail without falling back to direct execution.
Both paths invalidate shared nodes before mutation. Apply reads the configured
node output, validates it, publishes the shared node artifact and returns
`artifact`, `nodes` and `valid`. Destroy verifies empty managed state, collects
outputs and rejects any remaining nodes. It returns `destroyed` and
`managed_state_empty` plus `artifact`, `nodes: 0` and `valid: false`; the empty
node artifact prevents downstream commands from using deleted hosts. Output
collection is part of apply and destroy. Refresh-only and destroy saved plans
remain distinct modes.

```sh
bin/inframill instance exec example opentofu.apply --namespace production --stream
bin/inframill instance exec example opentofu.destroy --namespace production --stream
# To execute a specific saved plan:
bin/inframill instance exec example opentofu.apply --namespace production \
  --arguments '{"plan_id":"PLAN_ULID"}' --stream
```

Ansible supplies inventory, ping, syntax-check, check and apply. It consumes a bound node
artifact, selects the requested address without fallback, and checks the complete
host recap. Failed, unreachable, ignored or rescued failures reject. Check mode is a
prediction. Syntax-check needs no previously applied infrastructure. SSH uses an
agent and batch mode; Kit does not write private keys. The host-key policy defaults
to `strict`, which requires hosts to be trusted before connecting. Ansible sets
`UserKnownHostsFile` to the Instance's `artifacts/<configured-id>-known_hosts`
(normally `artifacts/ansible-known_hosts`). This file persists across executions,
rerenders and container replacements when the Instance data is persisted. For
`strict`, add verified host keys to this file before connecting; existing keys in
`~/.ssh/known_hosts` must be copied here if they should be trusted by Ansible.
The pv-cloud blueprint explicitly sets `host_key_policy: accept-new` to
automatically record unknown SSH hosts while still rejecting changed keys.

Dispatch is a separate provider using system SSH and SCP clients. Its `push` and
`make` commands read host records from shared artifacts, transfer directories
from `workspace/dispatch/` and run Make targets on selected nodes. Configure
payload mappings in `templates/dispatch/`; see [Dispatch usage](dispatch.md).

Use ping after OpenTofu apply to check SSH authentication and remote Python
without applying a playbook. It accepts optional `hosts`, but no playbook or tags:

`hosts` selects exact node names by filtering inventory before Ansible runs. Names
are never interpreted as group patterns. Service roles come from each node's
explicit `roles` list, independently of its name.

```sh
bin/inframill instance exec example ansible.ping --namespace production --stream
bin/inframill instance exec example ansible.ping --namespace production \
  --arguments '{"hosts":["web-1"]}' --stream
```

Ping uses `ansible.builtin.ping`, not ICMP, with a 30-second task timeout.
Ansible streams module/task status, safe connection failure categories and host
counters to stderr; arbitrary task results and arguments stay private. The pv-cloud
playbook waits up to 300 seconds for SSH while guests boot. A running execution
at that step is waiting for connectivity; restarting the daemon interrupts it.
The CLI's default two-minute timeout only stops waiting, so allow more time for
an apply after checking connectivity. `apply` defaults to the declared `site`
playbook; use `playbook` to select another declared playbook:

```sh
bin/inframill instance exec example ansible.apply --namespace production \
  --stream --timeout 15m
```

For current pv-cloud, follow guest preparation with the Dispatch payloads.
Select all three directories to deliver them in one push, then start them in
dependency order. Each payload still selects its own data, worker or web nodes:

```sh
bin/inframill instance exec example dispatch.push --namespace production \
  --arguments '{"directory":["postgres","inframill","millway"]}' --stream --timeout 15m
bin/inframill instance exec example dispatch.make --namespace production \
  --arguments '{"directory":["postgres","inframill","millway"],"target":"start"}' --stream --timeout 15m
```

The target waits for PostgreSQL readiness. Repeat pushes preserve its named volume
and refresh the required application password files from namespace secrets.
PostgreSQL uses host networking on port 5432 and requires TLS for external access; see
[pv-cloud](../blueprints/README.md#pv-cloud) for credentials and lifecycle commands.
Inframill uses native HTTPS directly on port 443 with Docker host networking, a
required root token and an independent persistent data volume on each selected
Linux worker. Port 443 must be available; Docker port publishing is not used.
Its private key and token are resolved from namespace secrets at push execution;
its public certificate is
rendered from Values. Install waits for the authenticated HTTPS API to respond.
For authenticated container pulls, set the optional pv-cloud `registry.host` and
`registry.username` Values and store `pv-cloud-registry-token` as a namespace
secret. All three payloads log in with the injected token before Compose starts and
stop installation if login fails. Omit `registry` to skip login. See the
[pv-cloud instructions](../blueprints/README.md#pv-cloud) for configuration.

For Docker, `task docker:up` mounts the project's `ssh/` directory at `/root/.ssh`.
Ansible and other providers invoking SSH use the standard identities there, such
as `ssh/id_ed25519`, along with `ssh/config`. Ansible stores known hosts in the
Instance artifacts described above. Other SSH providers use `ssh/known_hosts` by
default. Set directory permissions to `700` and private-key permissions to `600`.
For a nonstandard key
name, add an `IdentityFile /root/.ssh/your_key` entry to `ssh/config`. Paths in that
configuration must refer to the container filesystem. SSH can write `known_hosts`
to this mount, preserving trusted host keys across container replacements.
Re-run `task docker:up` to add the mount to an existing container.

Alternatively, load the matching private key into your host SSH agent with `ssh-add`.
`task docker:up` also forwards it when `SSH_AUTH_SOCK` is set, using Docker Desktop's
agent socket on macOS and the host socket on Linux. `KIT_SSH_AUTH_SOCK` overrides
the Docker-host socket path; set it to an empty string to disable forwarding.
The container can authenticate with keys loaded in that agent. Public keys in
blueprint values only authorize guest access; they do not supply client credentials.
Also check `ssh.user`, guest readiness, and that `ssh.source_ips` allows your client
address. Native daemons inherit the agent from the shell that starts them.

The executable's configured prefix is:

```text
/usr/local/bin/kit-exec opentofu-0.4.0
```

Inframill sends one JSON request on stdin, without adding protocol arguments. Kit
uses `pkg/runmill.Serve` for JSON Lines messages and final success/error replies.
For a manual discovery probe, pipe this JSON to that prefix:

```json
{"protocol":1,"method":"info","params":{}}
```

## Execution context and state

Runmill supplies settings, workspace/artifact paths and an execution ID, without
Instance or Blueprint metadata. Kit binds plans and node artifacts to a hash of
the supplied artifact directory. Regenerate plans and node output after moving
data to a different path. Execution IDs used for plan filenames must be canonical uppercase ULIDs (26 characters).

pv-cloud uses local OpenTofu state at
`<dataDir>/<namespace>/instances/<InstanceID>/artifacts/opentofu-terraform.tfstate`.
The filename uses the configured provider ID, so aliases have separate state.
State backups and named workspace states also live in artifacts. State is written
directly by OpenTofu, including during partially failed applies, and survives
Instance rerender. Blueprints using this backend must declare `backend "local" {}`.
The daemon's persisted data volume holds the state; no S3 bucket or AWS credentials
are required. Back up this storage and keep it until the managed infrastructure
has been destroyed. Deleting an Instance or namespace retains its local state on
disk, but hides it from normal engine APIs.

On existing local Instances, run `opentofu.init` with the updated provider before
rerender. Init migrates workspace state when the artifact state does not yet exist;
it does not force a migration over existing artifact state.

## RPC fields

RPC command submission uses `command_name` and `arguments: {"json":"..."}`.
Values, arguments, results and argument schemas use JSON document envelopes.
CLI JSON unwraps document envelopes into their JSON values; raw RPC clients retain
the `json` wrapper. Execution references use `execution_id`; statuses use `COMMAND_EXECUTION_STATUS_*`.
Provider discovery uses `ListProviders` and reports `availability`.
`ListCommandDefinitions` takes an empty request and returns cached commands from
all available providers, excluding built-in operations. It returns names,
descriptions and access modes without argument schemas. `GetBlueprint` publishes
the revision's selected commands and schemas; `ListInstanceCommandDefinitions`
returns that retained selection with provider metadata and the three engine-owned
built-ins. Use `inframill instance commands INSTANCE --namespace ID -o json` to
inspect the complete Instance contract. The former `instance_id` field on global
discovery is reserved.

Every namespace-owned RPC requires exactly one `X-Namespace-ID` header containing
a valid namespace ID. Namespace selectors are absent from request bodies and
response resources. Missing, empty, duplicate or padded headers reject; foreign
Instance IDs return not-found. The header selects scope and is not authentication.

`CreateNamespace`, `GetNamespace`, `ListNamespaces`, `DeleteNamespace`,
`GetServerVersion`, `ListProviders` and `ListCommandDefinitions` require the header
to be absent. `GetNamespace` accepts `{"id":"production"}` and returns the
namespace identity and lifecycle status.

`ListBlueprints`, `ListNamespaceSecretNames`, `ListNamespaceRegistryHosts` and
`ListInstances` query only the selected namespace. Secret `names` contains objects
such as `{"name":"hetzner"}`; registry `hosts` contains objects such as
`{"host":"ghcr.io"}`. Instance lists retain pagination; execution history remains
scoped to an Instance. Cursors cannot be reused in another namespace.
